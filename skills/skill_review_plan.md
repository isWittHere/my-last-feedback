# 如何审查规划方案

## 工具

```text
inspector_submit(passed=<bool>, content=<审查报告>)
```

- `passed=true` 表示本次审查通过
- `passed=false` 表示需要返工
- 调用后阻塞，直到下一条指令到达

## 审查原则

- **独立性**：不受方案自述影响，亲自验证关键技术声明
- **建设性**：每条问题给出具体修复建议和位置
- **聚焦**：关注实质问题，不纠结风格偏好
- **一致性**：上轮的「必须修复」未被修复则本轮继续标记
- **进步性**：方案合理回应反馈（即使做法不同于建议）应当认可

## 审查维度（6 项）

| # | 维度 | 检查要点 |
|---|------|----------|
| 1 | 需求完整性 | 原始需求的每个要点是否都有对应条目 |
| 2 | 技术可行性 | 技术方案是否合理，是否有更优选择 |
| 3 | 架构一致性 | 是否与现有架构兼容，是否引入不必要复杂度 |
| 4 | 风险评估 | 是否识别关键风险及应对措施 |
| 5 | 阶段划分 | Phase 划分是否合理，依赖关系是否正确 |
| 6 | 验收标准 | 每个 Phase 是否有明确、可验证的验收标准 |

## 勘察准备

- 读取 `AGENTS.md` 了解项目架构与规范
- 浏览与方案相关的核心代码文件，了解现状
- 不要仅依赖方案描述

## 决策级别

每条问题必须标注级别，参考 `skill_decision_levels`。

## 规划审查报告模板

```markdown
# 规划审查报告: 第 {N} 轮

## 审查背景
{本次审查对象：第几轮方案、相比上轮主要修改了什么}

## 疑似问题列表

### ISSUE-1: {问题标题}
- **位置**: {方案中的相关章节/Phase}
- **描述**: {问题描述}
- **严重度**: 高 / 中 / 低
- **决策级别**: **必须修复** / **建议改进** / **自行决定**
- **建议方案**: {如何修复}

## 高风险项
- ⚠️ {风险描述} — 影响范围: {描述} — 建议应对: {措施}

## 改进建议

### SUG-1: {建议标题}
- **决策级别**: **建议改进** / **自行决定**
- **当前方案**: {现在怎么做的}
- **建议方案**: {建议怎么做}
- **理由**: {为什么更好}

## 综合评判
- **结论**: 通过 / 未通过（对应 `passed` 参数）
- **必须修复项数量**: {N}
- **建议改进项数量**: {N}
- **投票意向**: pass / reject
- **投票理由**: {简要说明}
```

## 附加检查

- 若方案中出现委派表述（「已委派」「sub-task delegated」等）→ 直接判定幻觉，参考 `skill_hallucination_check`
