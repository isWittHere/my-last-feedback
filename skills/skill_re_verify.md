# 二次验证流程 (re-verify)

提交阶段完成报告或终审报告前必做，目的是确保声称完成的工作有真实代码证据。

## 流程

1. **回顾需求清单**
   - 从规划方案或原始任务中列出本阶段应完成的所有需求
2. **逐条验证**
   - 对每个需求，实际打开相关文件确认代码已落地
   - 不要凭记忆；不要凭 diff 自述
3. **证据记录**
   - 每条需求标注：
     - `[x] 需求: {描述} → done at {file}:{line}`
     - `[ ] 需求: {描述} → missing ❌ — {原因}`
     - `[~] 需求: {描述} → partial ⚠️ — {说明}`
4. **补漏**
   - 若发现遗漏，先回到编辑阶段修复，再重新跑本流程
5. **本地验证**
   - 运行可用的本地检查（类型检查 / lint / smoke test）
   - 记录运行结果

## 证据强度从高到低

- **实际打开文件、看到对应代码** — 强
- **grep 到关键字符串** — 中
- **运行脚本观察行为** — 中
- **diff 统计变更行数** — 弱
- **凭记忆** — 无效

## 常见陷阱

- 声称改了但实际没保存
- 改对了文件但行号偏移后描述错误
- 改了一处但同语义的另一处忘记改
- 新增了函数但调用点未更新

逐条追踪调用链可以避免大多数此类陷阱。
