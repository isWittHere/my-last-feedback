# 如何审查执行阶段产出

## 工具

```text
inspector_submit(passed=<bool>, content=<审查报告>)
```

- `passed=true` 通过本 Phase
- `passed=false` 要求修复后重交

## 审查原则

- **不信报告自述**：直接打开代码文件验证每条变更
- **独立验证**：对关键逻辑跟踪调用链，确认完整性
- **覆盖检查**：方案里列出的每条需求是否都有对应代码
- **补漏**：检查是否有专家忘记提到的文件变更

## 审查维度（6 项）

| # | 维度 | 检查要点 |
|---|------|----------|
| 1 | 需求覆盖 | 规划中列出的每条需求是否都有对应代码实现 |
| 2 | 代码正确性 | 逻辑是否正确，边界条件是否处理 |
| 3 | 架构一致性 | 是否遵循项目架构模式，是否引入不必要耦合 |
| 4 | 安全性 | 是否有 OWASP Top 10 风险（注入、认证、XSS 等） |
| 5 | 编码规范 | 命名、格式、注释是否符合项目约定 |
| 6 | 测试覆盖 | 关键路径是否有测试，测试是否有效 |

## 验证方法

- 对专家声称修改的每个文件都实际打开看一眼
- 对关键逻辑读一遍完整调用路径
- 检查是否有专家未提及但实际被修改的文件

## 决策级别

参考 `skill_decision_levels`。

## 代码审查报告模板

```markdown
# 代码审查报告: Phase {N}

## 审查范围
{审查了哪些文件、哪些功能模块}

## 需求覆盖检查
- [x] 需求: {描述} → 已确认实现 at `{file}:{line}`
- [ ] 需求: {描述} → 未实现 ❌ — {原因}
- [~] 需求: {描述} → 部分实现 ⚠️ — {缺失的部分}

## 问题列表

### BUG-1: {Bug 标题}
- **位置**: `{file}:{line}`
- **描述**: {问题描述}
- **严重度**: 高 / 中 / 低
- **决策级别**: **必须修复**
- **复现路径**: {如何触发}
- **建议修复**: {具体方案}

### ISSUE-1: {问题标题}
- **位置**: `{file}:{line}`
- **描述**: {描述}
- **决策级别**: **建议改进** / **自行决定**
- **建议方案**: {如何改进}

## 安全检查
- [ ] 无 SQL 注入风险
- [ ] 无 XSS 风险
- [ ] 无认证/授权绕过
- [ ] 输入验证完备
- {如有安全问题，列入问题列表并标「必须修复」}

## 综合评判
- **结论**: 通过 / 未通过（对应 `passed` 参数）
- **必须修复项**: {N} 项
- **建议改进项**: {N} 项
- **代码质量评分**: {A/B/C/D}
```

## 附加检查

- 若报告中出现委派表述 → 参考 `skill_hallucination_check`，直接标「必须修复」打回
