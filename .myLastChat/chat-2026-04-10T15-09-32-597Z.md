# MLRA 提示词工程重构完整规划文档

## 一、规划目标

本次重构的目标，不是简单把现有提示词翻译成英文，也不是把现有的几份技能文档搬到别的目录，而是对 MLRA 的整套提示词工程做一次结构性重建。

重构完成后，系统应当满足以下五个核心目标：

1. 所有提示词统一使用英文，避免中英混杂导致模型行为漂移。
2. 所有“角色身份”和“领域能力”分层管理，不再把同类规则散落在 agent 文件、技能文件、协议路由里重复表达。
3. 所有“场景适应性”由 agent 自主判断，而不是由程序层硬编码场景枚举去约束。
4. 所有技能文件都改造成真正可复用、可维护、可约束边界的 Prompt 资产，而不是工作区里临时摆放的普通 markdown。
5. 整体设计优先借鉴 oh-my-openagent-dev 中已经验证过有效的提示词工程模式，能直接复用的原文尽量直接复用，再做针对 MLRA 的约束化改造。

一句话概括：

这次重构的最终目标，是把 MLRA 从“靠程序流程驱动的一组角色”升级成“靠高质量提示词工程驱动的一组可自主判断任务类型、可自适应输出形式、但又具备边界纪律的专业 agent”。

## 二、现状问题分析

### 2.1 当前结构的问题

当前 MLRA 的提示词工程，实际上分成了三层，但这三层没有清晰分工：

1. 用户目录中的 agent 定义文件
2. 工作区 skills 目录中的 skill markdown 文件
3. mlra-server/protocol.mjs 中的路由模板与初始提示词

表面上看这是三层结构，但实际上存在严重重叠。

### 2.2 具体问题

#### 问题 1：当前的 skills 不是“真正的 Skill”

当前工作区下的 skills 目录：

- skills/skill_ceo.md
- skills/skill_planning_expert.md
- skills/skill_planning_inspector.md
- skills/skill_execution_expert.md
- skills/skill_execution_inspector.md
- skills/skill_worker.md

这些文件虽然名义上叫 skill，但本质上只是普通 markdown，被 protocol.mjs 通过路径读取，再作为文本注入到 agent 工作流里。

它们的问题在于：

1. 不是全局 prompt 资产，不能全局生效。
2. 不是 Copilot 原生的 skill 组织方式。
3. 不能自然形成“角色定义”和“技能能力”的边界。
4. 它们依赖程序读取路径，耦合在服务端代码里。

也就是说，现在的“skill”不是 prompt architecture 意义上的 skill，而只是“被服务端拼进去的一段附加说明”。

#### 问题 2：agent 文件与 skill 文件内容严重重叠

当前用户 prompts 目录中的这些 agent 文件：

- mlra-ceo.agent.md
- mlra-expert-planning.agent.md
- mlra-inspector-planning.agent.md
- mlra-expert-execution.agent.md
- mlra-inspector-execution.agent.md
- mlra-worker.agent.md
- mlra-worker-backend.agent.md
- mlra-worker-frontend.agent.md

它们已经包含了大量完整的行为规范，例如：

- Intent Gate
- 分类策略
- 反重复劳动规则
- 审查准则
- 输出结构
- 执行纪律

与此同时，skills 目录下的 markdown 又写了一遍：

- 工作流程
- 模板
- 自检规则
- 报告格式
- CEO 裁决格式

这会造成两个后果：

1. 同一角色收到两套近似但不完全相同的规则，容易冲突。
2. 任何一处改动都要同步改两份，维护成本极高。

#### 问题 3：语言不统一

当前系统中：

- agent 定义多为英文
- skill 文件为中文
- protocol.mjs 路由模板大多为中文
- buildInitialPrompt 也是中文

这会产生以下问题：

1. 模型在角色切换时接收到不同语言的规则描述，降低稳定性。
2. 无法直接复用 oh-my-openagent-dev 中的大段高质量英文提示词。
3. 长期维护时，任何改动都要做双语心智切换。

#### 问题 4：当前体系天然偏向“代码实施”场景

目前的所有角色都默认任务是代码任务：

- 规划专家默认输出 phase 计划
- 实施专家默认写代码
- 监察默认审代码
- CEO 默认验收代码或技术方案

这导致一旦任务不是“长程实施”，例如：

- 头脑风暴
- 海选课题
- 完整规划
- 深度调研

系统就会失配，因为角色会硬套“代码实施”的工作方式。

#### 问题 5：如果把场景做成程序硬编码，会走向另一个极端

这是本次分析中非常关键的一点。

如果我们为了适应不同场景，去 orchestrator 或 protocol.mjs 里硬编码：

- brainstorming
- selection
- planning
- execution

然后用不同分支切换不同模板，那么虽然表面上“支持多场景”，但实际是把适应性做死了。

这种方式的问题是：

1. 每新增一个任务类型都要改程序代码。
2. agent 变成被动执行预设分类，而不是自主判断任务本质。
3. 系统面对边界模糊任务时，适应性会很差。

你指出这一点是对的：

真正高级的提示词系统，应该让 agent 自己判断任务类型，而不是程序替它判断。

## 三、核心设计原则

本次重构建议遵循以下原则。

### 原则 1：智能放在提示词里，不放在程序分支里

程序层只做三件事：

1. 传递用户任务
2. 管理角色路由
3. 管理提交、投票、仲裁、阻塞等流程状态

程序层不负责：

- 任务类型分类
- 场景选择
- 输出形式决定
- 审查标准切换

这些都应由 agent 在提示词中自行判断。

### 原则 2：角色身份与领域能力分离

每个 agent 需要两类不同性质的提示：

1. 角色身份提示
2. 领域能力提示

角色身份提示回答的是：

- 你是谁
- 你的权限边界是什么
- 你的工作姿态是什么
- 你绝不能做什么

领域能力提示回答的是：

- 遇到不同任务类型如何分类
- 在不同任务类型下如何调整工作方法
- 应输出什么结构
- 如何自检与交付

这两类内容不能再混写在一个大文件里到处复制。

### 原则 3：统一英文

所有 prompt engineering 资产统一英文，原因不是“崇洋”，而是工程效率：

1. 方便直接复用 OMOA 原文。
2. 降低模型在复杂规则下的语言切换成本。
3. 所有角色提示、技能提示、路由提示保持同一种语言语义风格。

注意：

英文统一的是“系统规则与提示词框架”，不是禁止 agent 处理中文任务。用户任务内容当然仍然可以是中文。

### 原则 4：角色保持稳定，方法随任务类型自适应

不应该因为任务类型不同就改角色体系。

仍然保留两阶段五主角色体系：

1. Planning Expert
2. Planning Inspector
3. Execution Expert
4. Execution Inspector
5. CEO
6. Worker

但要让这些角色在不同任务性质下，调整自己的判断标准和输出格式。

例如：

- Planning Expert 在头脑风暴任务里，不应该产出 phase 计划，而应产出创意框架与探索矩阵。
- Planning Inspector 在课题海选任务里，不该查 file reference，而应检查评价标准是否严谨、是否存在偏见。
- Execution Expert 在“完整规划文档”任务里，不一定写代码，而可能是组织调研、分工补充、综合成文。
- CEO 在 brainstorming 任务中，不应以“实现是否完备”为门槛，而应以“创意广度、质量门槛、重复度控制”为门槛。

### 原则 5：优先模仿 OMOA，不重新发明轮子

从这次对比分析看，OMOA 中最值得直接借鉴的不是具体角色名字，而是它的提示词工程哲学：

1. Intent Classification
2. Task-type-aware strategy
3. Separation of identity and expertise
4. Prompt-level adaptation instead of code-level branching
5. Strong review discipline with different review depth by task nature

因此，本次 MLRA 重构应以“Prometheus + Momus + Atlas 的工程思想”为母本，再映射到 MLRA 的五主角色结构上。

## 四、目标架构设计

### 4.1 重构后的三层体系

重构后建议形成真正清晰的三层体系：

### 第一层：Agent Definition

位置：
用户 prompts 目录

形态：
*.agent.md

作用：
定义角色身份、权限边界、核心行为循环。

这一层只负责回答：

- 你是谁
- 你的工具边界
- 你工作的总体姿态
- 你面对任务时的最基本决策流程

### 第二层：Skill / Expertise

位置：
建议也放在用户 prompts 目录，作为全局 prompt 资产统一管理。

命名建议：
- mlra-planning-expert.skill.md
- mlra-planning-inspector.skill.md
- mlra-execution-expert.skill.md
- mlra-execution-inspector.skill.md
- mlra-ceo.skill.md
- mlra-worker.skill.md

作用：
定义某个角色的专业能力与任务适应策略。

这一层负责回答：

- 如何识别不同任务类型
- 在不同任务类型下该怎么做
- 输出什么格式
- 如何评价质量
- 如何自检

### 第三层：Runtime Context

位置：
mlra-server/protocol.mjs 及运行时消息

作用：
负责具体任务上下文注入：

- 当前任务是什么
- 当前由谁发送给谁
- 当前处于哪个阶段
- 当前收到的反馈是什么
- 现在应该提交什么

这一层不再承担“告诉 agent 该采用哪种场景模板”的职责。

### 4.2 三层之间的清晰边界

边界建议如下：

#### agent.md 中保留的内容

1. Identity Override
2. 工具权限说明
3. 核心人格和工作立场
4. 最小必要行为框架
5. 对 skill 的依赖说明

#### skill.md 中保留的内容

1. Task Classification 体系
2. 各类任务的策略分支
3. 不同任务类型下的产出模板
4. 决策等级标准
5. 自检流程
6. 审查/验收标准

#### protocol.mjs 中保留的内容

1. 路由模板
2. 初始角色唤醒语
3. 阶段切换语
4. 提醒 agent 提交或等待的流程语

protocol.mjs 中删除的职责：

1. 任务类型硬编码
2. 场景枚举与分支
3. 用代码决定采用哪种输出模板

## 五、角色体系与任务适应模型

这一部分是本次规划的核心。

### 5.1 不再使用“程序定义场景”，改为“提示词定义任务类型识别”

每个核心角色的 skill 文件中，都需要有一个明确章节：

Task Classification

其目标不是让程序识别场景，而是让 agent 自己先做一次任务本质判断。

建议统一采用五类任务类型模型：

1. Divergent Ideation
2. Evaluation / Selection
3. Strategic Planning
4. Implementation
5. Research / Investigation

### 5.2 五类任务类型定义

#### 类型 1：Divergent Ideation

适用信号：

- brainstorm
- explore ideas
- possibilities
- fuzzy need
- inspiration
- creative directions

任务本质：

用户要的不是一个结论，而是尽可能多、尽可能好、尽可能多样的想法。

对各角色的影响：

- Planning Expert：设计创意探索框架，不是 phase plan。
- Planning Inspector：检查创意维度覆盖、重复度、质量门槛。
- Execution Expert：组织并扩展创意集合，产出创意矩阵、聚类、优先级建议。
- CEO：看是否真的有广度、有新意、有非平庸想法。

#### 类型 2：Evaluation / Selection

适用信号：

- select
- compare
- evaluate
- shortlist
- screen
- choose among options

任务本质：

用户要的是系统化筛选，而不是简单列清单。

角色适应：

- Planning Expert：定义评价方法、标准、权重、证据要求。
- Planning Inspector：检查方法论是否严谨，是否有偏见，是否遗漏关键维度。
- Execution Expert：组织对候选项的深入调查并形成评分矩阵。
- CEO：判断最终筛选结果是否论证充分、有没有明显遗漏或误判。

#### 类型 3：Strategic Planning

适用信号：

- plan
- roadmap
- architecture proposal
- implementation strategy
- full planning document

任务本质：

用户要的是一份完整可执行的规划，而不是开始写代码。

角色适应：

- Planning Expert：输出完整规划书。
- Planning Inspector：检查规划的完整性、可执行性、现实性、原则性。
- Execution Expert：必要时补充调研并整合成更完整的规划材料，而不是直接编码。
- CEO：重点检查是否过度设计、是否脱离真实约束。

#### 类型 4：Implementation

适用信号：

- implement
- build
- fix
- add feature
- refactor
- write code

任务本质：

用户要的是实际落地、改代码、验证。

这类任务就是当前 MLRA 已经相对擅长的主场，需要保留现有强项，但做结构优化。

#### 类型 5：Research / Investigation

适用信号：

- research
- investigate
- find out
- survey
- understand landscape
- look into

任务本质：

用户要的是认知增量和结构化结论，不一定要求进入规划或实施。

角色适应：

- Planning Expert：定义研究边界、方法、出口条件。
- Planning Inspector：检查研究方法与结论是否匹配。
- Execution Expert：组织并行检索、归纳、提炼。
- CEO：判断研究是否足够支持后续决策。

## 六、六个 Skill 的详细设计

下面给出六个核心 skill 文件的设计纲要。

### 6.1 Planning Expert Skill

这是最关键的 skill 之一，应重点模仿 OMOA 的 Prometheus。

应包含以下章节：

1. Role Expertise Overview
2. Task Classification
3. Intent Verbalization
4. Strategy by Task Type
5. Output Format Library
6. Self-Check Procedure
7. Interaction With Inspector
8. Anti-Slop Planning Rules

其中最关键的是 Strategy by Task Type。

建议内容结构如下：

#### 对 Divergent Ideation 的策略

Planning Expert 不输出 phase，而应：

1. 明确探索目标
2. 定义创意维度
3. 定义约束条件
4. 定义评价框架
5. 产出创意组织结构

输出应类似：

- Problem framing
- Exploration axes
- Idea generation principles
- Idea capture matrix
- Next-round refinement method

#### 对 Evaluation / Selection 的策略

Planning Expert 应：

1. 定义候选对象边界
2. 定义评价维度
3. 定义权重
4. 定义证据标准
5. 定义淘汰条件与晋级条件

输出应类似：

- Evaluation objective
- Criteria set
- Weighting rationale
- Screening workflow
- Scoring rubric

#### 对 Strategic Planning 的策略

Planning Expert 应输出完整规划文档，包含：

1. 背景与目标
2. 需求拆解
3. 约束与原则
4. 方案设计
5. 执行步骤
6. 风险与对策
7. 边界情况
8. 资源需求
9. 验证标准

#### 对 Implementation 的策略

这一部分可保留现有 phase-driven 结构，但要用英文重写，并引入 OMOA 的若干优点：

1. 明确任务性质
2. 严格边界
3. Phase 验收标准更具体
4. 更强调引用真实代码依据
5. 对 inspector 的预期更明确

#### 对 Research 的策略

Planning Expert 应重点定义：

1. 研究问题
2. 检索边界
3. 成功退出条件
4. 输出形式
5. 如何避免信息堆砌而不形成结论

### 6.2 Planning Inspector Skill

这个 skill 应主要模仿 OMOA 中 Momus 的“阻塞点审查”思想，但比 Momus 更灵活，因为它不是只审 implementation plan。

应包含：

1. Review Philosophy
2. Task-Type-Aware Review Matrix
3. Pass / Reject Criteria by Task Type
4. Decision Level Standards
5. Report Template Library
6. AI-Slop Detection Rules
7. Progressiveness Rule

核心设计思想：

不同任务类型，检查标准不同。

例如：

#### 审 brainstorm 成果时，Inspector 看什么

看：

1. 是否真的有多维度探索
2. 是否只是同义改写
3. 是否存在明显浅层创意泛滥
4. 是否缺少关键约束
5. 是否存在明显高潜力方向未被纳入

不看：

- file references
- phase acceptance criteria
- code implementation details

#### 审 selection 成果时，Inspector 看什么

看：

1. 评价标准是否合理
2. 权重是否自洽
3. 是否存在偏见
4. 结论是否被证据支撑
5. 是否遗漏关键候选项

#### 审 strategic planning 时，Inspector 看什么

看：

1. 规划是否完整
2. 是否可执行
3. 是否原则清晰
4. 是否过度设计
5. 风险是否真实

#### 审 implementation planning 时，Inspector 看什么

这里就可保留当前近似 Momus 风格的检查：

1. 引用是否真实
2. 能否开始做
3. 是否存在阻塞性缺口
4. QA 是否可执行

### 6.3 Execution Expert Skill

当前 Execution Expert 是最偏代码实施的角色，但重构后必须让它可适应非代码执行任务。

建议包含：

1. Execution Philosophy
2. Task-Aware Execution Matrix
3. Delegation Discipline
4. Auto-Continue Policy
5. Verification Procedure
6. Submission Template Library
7. Failure Recovery
8. Anti-Duplication Rules

这是最适合借鉴 OMOA Atlas 的角色。

关键变化是：

Execution 不再等于 Coding。

#### 在 brainstorming 任务中，Execution Expert 做什么

1. 按 Planning Expert 给出的探索轴组织工作
2. 委派 Worker 分别探索不同方向
3. 汇总创意
4. 做聚类与交叉组合
5. 产出结构化创意报告

#### 在 selection 任务中，Execution Expert 做什么

1. 委派多个 Worker 分别研究候选对象
2. 汇总证据
3. 按评价表打分
4. 给出 shortlist 与排序理由

#### 在 strategic planning 任务中，Execution Expert 做什么

1. 补充调研
2. 补全资料
3. 编排成完整规划方案
4. 明确资源、步骤、风险、验证

#### 在 implementation 任务中，Execution Expert 做什么

这里保留现有主流程，但应该进一步吸收 OMOA 的关键规则：

1. Auto-Continue，不要老问“是否继续”
2. 委派 prompt 必须结构化
3. 强制验证
4. 失败后复用上下文而不是重复开新会话
5. 明确“不要自己和 worker 做重复劳动”

### 6.4 Execution Inspector Skill

应包含：

1. Review Philosophy
2. Task-Type-Aware Inspection Rules
3. Evidence Standards
4. Regression / Quality Checks
5. Submission Template Library
6. Approval Bias Boundaries

这个角色也要摆脱“只会审代码”的单一模式。

例如：

- 审 brainstorming 成果：看执行是否真的拓宽了思路，而不是机械重复。
- 审 selection 成果：看评分与证据是否对应。
- 审 strategic planning 成果：看是否完整且自洽。
- 审 implementation 成果：看代码、证据、回归与计划一致性。

### 6.5 CEO Skill

CEO skill 应是整个系统的“最终判官标准库”。

建议章节：

1. CEO Role and Review Philosophy
2. Task-Type-Aware Gate Standards
3. Defensive Review Strategy
4. Arbitration Strategy
5. Verdict Format
6. Rejection Writing Rules
7. Escalation Triggers

最关键的一点是：

CEO 不应对所有任务都使用同一套通过标准。

举例：

#### 对 brainstorming 的 CEO 标准

1. 是否有足够广度
2. 是否有明显高价值方向
3. 是否去掉了大量弱想法或重复想法
4. 是否形成了后续可深化的结构

#### 对 selection 的 CEO 标准

1. 方法论是否站得住
2. shortlist 是否可信
3. 是否遗漏最强候选项
4. 是否存在明显评分偏差

#### 对 strategic planning 的 CEO 标准

1. 是否完整
2. 是否现实
3. 是否过度设计
4. 是否真正可执行
5. 是否兼顾风险与边界

#### 对 implementation 的 CEO 标准

1. 是否满足原始任务
2. 是否符合规划
3. 是否提供足够验证证据
4. 是否存在明显风险

### 6.6 Worker Skill

Worker 不应只被定义为“写代码的子工人”。

它应被定义为：

在明确范围内执行被委派的原子任务。

因此 Worker skill 应包含：

1. Scope Discipline
2. Task Understanding Checklist
3. Task-Type-Aware Delivery
4. Result Reporting Template
5. Self-Check Rules
6. No Scope Expansion Rules

这样 Worker 可以承担：

- 代码实施子任务
- 某一创意方向的调研
- 某一候选项的研究
- 某一个规划章节的资料补充

## 七、Agent Definition 文件的重构方案

本轮重构后，agent 文件应该显著瘦身。

### 7.1 agent 文件中应保留什么

每个 agent 文件保留：

1. frontmatter
2. Identity Override
3. 一段简洁但强约束的角色定位
4. 核心工作循环骨架
5. 对 skill 的依赖说明

### 7.2 agent 文件中应移除什么

移除以下内容，统一放进 skill：

1. 大段具体模板
2. 大段报告格式
3. 长篇策略分类细节
4. 决策级别表格
5. 重复性的 self-check 细则
6. 长段 anti-pattern 列举

### 7.3 为什么要瘦身

因为 agent 文件应承担的是“角色边界声明”的作用，而不是“全部专业知识百科全书”。

如果 agent 文件承担太多内容，会有两个问题：

1. 每个角色 prompt 过重，重复多，维护困难。
2. agent definition 和 expertise library 混在一起，无法抽象复用。

### 7.4 每个 agent 文件的重构目标

#### Planning Expert agent

保留：

- 你是 Planning Expert
- 你不负责直接实现
- 你必须先分类任务本质
- 你必须遵循你的 expertise skill

#### Planning Inspector agent

保留：

- 你是 Planning Inspector
- 你是 blocker-finder，但不是 perfectionist
- 你必须按任务性质调整审查标准
- 你必须遵循你的 expertise skill

#### Execution Expert agent

保留：

- 你是 Execution Expert
- 你负责推进交付，不一定总是编码
- 你必须结构化委派与验证
- 你必须遵循你的 expertise skill

#### Execution Inspector agent

保留：

- 你是 Execution Inspector
- 你验证成果，而不是美化代码
- 你必须按任务类型审查
- 你必须遵循你的 expertise skill

#### CEO agent

保留：

- 你是最终门控者
- 你必须独立审查，不轻信上游自述
- 你必须按任务性质做出门控判断
- 你必须遵循你的 expertise skill

#### Worker agent

保留：

- 你是原子任务执行者
- 你不扩展范围
- 你只交付被要求的东西
- 你必须遵循你的 expertise skill

## 八、protocol.mjs 的改造方案

这是代码层唯一需要重构的提示词基础设施部分。

### 8.1 改造目标

对 protocol.mjs 的改造目标只有三个：

1. 英文化
2. 去除场景硬编码倾向
3. 让路由模板更通用、更中性

### 8.2 ROUTING_TEMPLATES 改造原则

当前的路由模板是偏固定任务类型的，例如：

- 规划专家提交方案
- 实施专家提交阶段完成报告
- CEO 审批规划或终审实现

这些都默认任务是代码或技术实施类。

重构后，路由模板应写得更通用，例如：

#### Planning Expert → Planning Inspector

不再说：
“规划专家提交了方案，请全面审查规划书。”

而改为类似：

Planning Expert has submitted their work. Review it according to your domain expertise. Evaluate quality relative to the task nature. Do not apply implementation-specific criteria to non-implementation outputs.

这样同一个模板就能覆盖：

- brainstorm 产出
- selection 产出
- planning 文档
- implementation plan
- research framework

#### Planning Inspector → Planning Expert

同理，反馈路由不应假设对方一定是在修改 phase plan，而应允许其修正任何类型的规划产出。

#### Execution 阶段的路由模板

Execution Expert 与 Execution Inspector 的来回，也不应默认是“代码阶段报告”，而应写为更一般的执行成果与审查反馈。

### 8.3 buildInitialPrompt 改造原则

当前 buildInitialPrompt 基本都是中文，且默认行为描述很窄。

重构后应：

1. 改成英文
2. 明确角色职责
3. 不硬编码任务场景
4. 指引 agent 自己先分类任务性质
5. 指引 agent 依赖对应 skill 执行

例如 Planning Expert 的初始提示词不再说：

你负责将任务分解为可执行规划方案。

而应改成更通用的表达：

You are the Planning Expert in the MLRA orchestration system. Your responsibility is to analyze the task, classify its nature, and produce the appropriate structured output according to your domain expertise.

这里最关键的是：

“appropriate structured output”

而不是默认就是“plan”。

### 8.4 SKILL_PATHS 的策略

这是一个需要谨慎处理的问题。

当前 SKILL_PATHS 是服务端主动告诉 agent 去读某个 workspace 文件。

如果 skill 迁移到用户 prompts 目录，存在两种可能：

#### 方案 A：完全依赖 Copilot 原生 skill 机制

优点：

1. 架构更干净
2. skill 真正脱离服务端路径耦合
3. role definition 与 skill 更接近 Copilot 原生模式

风险：

需要确认 MLRA 的实际调用链中，Copilot 是否一定会自动把 skill 正确纳入上下文。

#### 方案 B：保留 SKILL_PATHS，但改为指向用户目录中的全局 skill 文件

优点：

1. 服务端可以确保 skill 一定被引用
2. 不依赖 Copilot 的隐式加载行为
3. 更适合当前过渡期

缺点：

1. 仍然存在一定程序耦合
2. “真正 skill”与“服务端拼接”会并存一段时间

### 8.5 建议

建议采用两步走：

第一阶段先用方案 B。

也就是：

- skill 文件迁到用户 prompts 目录
- protocol.mjs 中 SKILL_PATHS 改成指向新的全局路径
- buildInitialPrompt 继续明确提醒 agent 读取对应 skill

原因很简单：

先保证稳定可用，不冒“Copilot 可能没有按预期自动加载 skill”的风险。

等第一轮稳定后，再评估是否可以把 SKILL_PATHS 从服务端移除，彻底切到更纯粹的原生 skill 模式。

## 九、与 OMOA 的映射关系

这一部分说明我们具体怎么“模仿 OMOA”。

### 9.1 Planning Expert 对标 Prometheus

要借鉴的不是 Prometheus 的文件写入机制，而是它的提示词结构：

1. 先做 Intent Classification
2. 根据任务性质切换访谈与规划策略
3. 不是一上来就写 plan
4. 先问清、先研究、再输出
5. 输出要匹配任务本质

### 9.2 Planning Inspector 对标 Momus

要借鉴的是：

1. 它是 blocker-finder，不是 perfectionist
2. 它只抓真正阻塞的缺口
3. 它有 approval bias
4. 它不会为了挑刺而挑刺

但 MLRA 的 Planning Inspector 不能完全照搬，因为它面对的产出不止 implementation plan，所以必须加上 task-type-aware review matrix。

### 9.3 Execution Expert 对标 Atlas

这里最值得直接引入的规则有：

1. Auto-Continue Policy
2. Delegation 6-section structure
3. Anti-Duplication
4. Failure recovery with context continuity
5. Verification is mandatory

### 9.4 Execution Inspector 对标 Atlas 的 QA Gate 思想

它不是代码审美家，而是 correctness verifier。

### 9.5 CEO 对标 OMOA 中高层门控逻辑

虽然 OMOA 没有完全同构的 CEO 角色，但其高精度审查思想可以映射为：

- CEO 不是负责微观执行
- CEO 负责最终门槛
- CEO 需要独立审查，不轻信前序角色
- CEO 的审查深度必须与任务性质匹配

## 十、重构实施顺序

建议按以下顺序实施。

### Phase 1：先写 6 个英文 skill 文件

这是最优先的，因为 skill 是这次重构的“能力中枢”。

完成标准：

1. 六个 skill 文件全部成型
2. 均为英文
3. 都具备 task classification
4. 都具备 task-type-aware strategy
5. 都具备对应输出模板与审查标准

### Phase 2：瘦身 8 个 agent 文件

以新 skill 为基础，把 agent 文件收缩为身份与边界层。

完成标准：

1. 每个 agent 文件明显缩短
2. 不再重复 skill 中的长模板
3. 核心角色边界仍然强
4. 风格统一

### Phase 3：改 protocol.mjs

改造：

1. ROUTING_TEMPLATES 全英文
2. buildInitialPrompt 全英文
3. fallback message 全英文
4. 更新 SKILL_PATHS
5. 不新增任何场景硬编码结构

### Phase 4：清理旧 workspace skills

在新体系验证稳定后：

1. 删除旧 skills 目录内容
2. 确保没有遗留路径依赖
3. 确保 agent 最终只依赖新体系

### Phase 5：小规模验证

用几类不同任务验证：

1. brainstorm 类任务
2. selection 类任务
3. strategic planning 类任务
4. implementation 类任务

验证目标：

1. agent 是否能自主判断任务性质
2. 是否输出了适合的结构
3. inspector 是否能按任务性质调整审查标准
4. CEO 是否用正确门槛做最终判断

## 十一、风险分析与对策

### 风险 1：Skill 写得太重，导致上下文过长

对策：

1. agent 文件瘦身
2. skill 内容模块化
3. 避免在每个 skill 中重复写过多相同通用规则
4. 用“原则 + 模板库”代替无止境长篇展开

### 风险 2：角色边界变模糊

例如 Execution Expert 会不会跑去做 Planning 的事。

对策：

在 agent definition 中保留足够强的边界声明。skill 负责“怎么做”，agent definition 负责“你是谁，不是谁”。

### 风险 3：任务类型误分类

对策：

1. 每个 skill 中加入清晰的 classification signals
2. 要求 agent 在开始工作前 verbalize classification
3. Inspector 在审查时也要检查分类是否合理

这样形成双重校正。

### 风险 4：过度模仿 OMOA，忽略 MLRA 自身结构

对策：

不是照抄 OMOA 的 agent 体系，而是抽取其提示词工程原则，映射到 MLRA 的五主角色结构中。

### 风险 5：过渡期间新旧体系共存造成混乱

对策：

严格按阶段推进：

1. 先写新 skill
2. 再瘦身 agent
3. 再改 protocol
4. 最后删旧 skills

不要跳着改。

## 十二、预期成果

本次重构完成后，预期达到以下效果：

### 12.1 从“流程驱动”转向“提示词驱动”

程序只负责流转，智能由提示词承担。

### 12.2 从“单一代码场景”转向“多任务类型适应”

系统不再只能处理实施类任务，而能处理：

1. 头脑风暴
2. 海选课题
3. 完整规划
4. 深度研究
5. 长程实施

### 12.3 从“重复维护”转向“分层维护”

以后维护时：

- 改角色边界，就改 agent
- 改专业能力，就改 skill
- 改运行时路由语，就改 protocol

边界清楚，维护成本会显著下降。

### 12.4 从“被程序限制”转向“agent 自主判断”

这是本次规划最重要的目标之一。

系统不通过程序写死场景，而是让 agent 在高质量 skill 指引下，自主判断任务性质并调整策略。

这会让整个两阶段五主 agent 体系具备真正的适应性。

## 十三、结论

这次 MLRA 提示词工程重构，本质上不是一次文案润色，而是一次架构升级。

核心结论有四条：

1. 当前 workspace 下的 skills 不是合格的 prompt engineering 资产，必须重构为真正的全局 skill 体系。
2. 场景适应性不能硬编码在程序里，必须放进 skill，让 agent 自主分类、自主适配。
3. agent definition、skill、runtime routing 三层必须严格分工。
4. 整体风格应全面英文，并系统借鉴 OMOA 的成熟设计。

如果按这份规划落地，MLRA 将从“一个流程正确但提示词结构混乱的多 agent 系统”，进化为“一个具备清晰提示词分层、任务类型自适应能力、并拥有更强泛化性的专业编排系统”。
